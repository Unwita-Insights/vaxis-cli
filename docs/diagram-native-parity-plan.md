# Item 7 — Make CLI `--mermaid` diagrams match Vaxis native-AI quality

**Goal:** a diagram authored by an external assistant (Claude, Codex, GLM, or another
agent) and submitted through `vaxis diagrams generate --mermaid` should approach the
structural and visual quality of a diagram generated by Vaxis's server AI through
`--prompt`.

Repos involved:

- `vaxis-cli`: CLI, local format reference, preflight lint, and `skill-data/core/SKILL.md`
- `vaxis`: API generation pipeline, native prompt, browser renderer, and scene serializer

Implementation PRs:

- `vaxis-cli` [#18](https://github.com/Unwita-Insights/vaxis-cli/pull/18)
- `vaxis` [#353](https://github.com/Unwita-Insights/vaxis/pull/353)

**Status reviewed:** 2026-07-22. Engineering phases 1–4 are substantially implemented;
Item 7 remains open until the Phase 0 captures, screenshot evidence, and measured
before/after results complete the acceptance criteria.

The native prompt is defined in `vaxis/apps/api/src/prompts.ts`.

---

## Executive conclusion

The main gap is **not a separate renderer or a missing general styling pipeline**.
Both inputs are stored as Mermaid and use the same deterministic Mermaid processing and
browser rendering. Most visible differences therefore originate in the graph authored by
the model: grouping, richness, hierarchy, direction, topology, and drill structure.

Item 7 should be treated primarily as a **graph-authoring contract and prompt-parity
problem**, supported by deterministic repair where sufficient context exists. It should
not be treated as a server-rendering rebuild.

This conclusion has one important qualification: shared normalization is a safety net,
not a guarantee that arbitrary assistant-authored Mermaid is semantically or visually
equivalent to native AI output.

## Verified current behavior

### Shared server text processing

The two generation paths converge on the same deterministic processing function:

```text
fixLeakedNodeIds → normalizeShapes → injectSpacing
```

- Native `--prompt` path: `runGenerate` processes the generated main Mermaid and drill
  Mermaid.
- Direct `--mermaid` path: `generateFromMermaid` processes the submitted main Mermaid and
  drill Mermaid.
- Both paths parse drill markers and only allow drills for flowcharts.

Relevant files in `vaxis`:

- `apps/api/src/services/diagram/generate_service.ts`
- `apps/api/src/utils/mermaid.ts`

### Shape normalization is shared but limited

`normalizeShapes` repairs rectangle syntax in two cases:

- A label matching a known storage keyword becomes a cylinder.
- A label ending in `?` becomes a rhombus.

This means both paths receive the same deterministic safety net for common storage and
decision shapes. It does **not** mean shape correctness is free. The transform does not:

- Decide whether every persistence concept is represented.
- Decide whether a question is genuinely a yes/no branch.
- Enforce the full semantic shape contract.
- Repair every unsupported Mermaid shape.
- Guarantee useful shape diversity.

The assistant must still select meaningful nodes, use supported syntax, and self-check
the resulting graph.

### Shared V2 browser styling

The V2 renderer applies a source-agnostic visual system after Mermaid conversion:

- Subgraph containers receive palettes by container order.
- Nodes inherit the palette stroke associated with their containing subgraph.
- Ungrouped nodes receive the default neutral styling.
- Container fills, node fills, strokes, typography, arrowheads, and roughness are assigned
  by the V2 styling pass.
- ELK performs the compound layout.

The previously uncertain palette claim has been verified in
`apps/web/src/lib/mermaid/v2/mermaidToSceneV2.ts`. V2 assigns palette indices by
subgraph-container order and overwrites the corresponding Excalidraw element colors.
Consequently, explicit Mermaid `style ... fill:` lines are not the source of the final
V2 palette.

This makes **subgraph membership load-bearing**, while explicit subgraph colors are at
most fallback compatibility for non-V2 rendering. The current `SKILL.md` explanation
that direct Mermaid has “no server-side styling pass” is factually incorrect and must be
rewritten.

### Direction handling is now context-aware on both paths

Native generation and direct Mermaid both use `applyFlowchartDirection`, but direct
Mermaid remains backward compatible. PRs #18 and #353 added optional
`direction_context` containing:

- `policy`: `preserve` (default) or `auto`.
- `explicit`: `LR` or `TB`; an explicit value always wins.
- `is_fresh_generation`: auto-direction is never applied to edits.
- `viewport`: auto-direction requires a known landscape viewport.

Requests that omit this context keep their authored Mermaid direction unchanged. This
prevents silent rewrites for old clients, edits, portrait canvases, and headless callers
whose viewport is unknown.

## What produces the visible quality gap

The largest differences are structural properties in the Mermaid text:

1. **Grouping:** related nodes must be placed into flat `subgraph` blocks so the renderer
   can apply meaningful container layout and palette styling.
2. **Richness:** named platforms should expand into relevant components when the user's
   intent calls for detail—for example, a platform may contain authentication, database,
   storage, and realtime capabilities rather than one generic box.
3. **Domain vocabulary:** non-software diagrams should use domain-appropriate nouns rather
   than generic software suffixes such as “Service”, “Module”, or “Engine”.
4. **Hierarchy:** roots should show major composites and leaf dependencies; composite
   internals belong in drill children.
5. **Topology:** layered DAGs normally render more clearly than hub-and-spoke graphs with
   excessive fan-out.
6. **Direction:** use LR for genuine pipelines and step chains; use TB for layered
   architectures and branching systems.
7. **Drill substance:** seeded children should contain useful structure, while bare drill
   markers remain valid when a child is intentionally created empty.

Native AI also has LLM-based backstops for hierarchy, minimum useful size, and thin drill
content. Reproducing those checks inside direct Mermaid would require another model call
and would defeat the quota-free purpose of `--mermaid`.

## Current `SKILL.md` parity

### Already covered

- Supported flowchart shape mapping and storage keywords
- Genuine question-to-rhombus guidance
- Forbidden new shapes and preserve-existing-node exception
- Flat subgraphs and suggested fallback colors
- Fan-out cap around four connections
- Composite-versus-leaf drill guidance
- Default drills for sufficiently large software architectures
- Drill marker placement and node-ID rules
- Preserve-on-edit behavior

### Added by PR #18

1. `S_RICHNESS`: expand named platforms and match detail to user intent.
2. `S_DOMAIN`: use domain-specific language outside software architecture.
3. Shape self-check: require a cylinder when persistence exists and a decision shape when
   genuine branching exists.
4. Layered-DAG guidance beyond the connection cap.
5. Strong LR pipeline versus TB architecture guidance.
6. Seeded drill substance: aim for at least three meaningful nodes without invalidating
   bare markers.
7. Correct explanation of shared processing and V2 palette behavior.

These rules are now mirrored in the embedded authoring contract and guarded by CLI tests.

## Revised implementation plan

### Phase 0 — Establish a measurable baseline

Create a small fixed evaluation set before changing prompts. Start with 10–20 prompts
covering:

- Layered software architecture
- Linear data pipeline
- Branching business process
- Named cloud/backend platform
- Database-heavy system
- Non-software domain
- Small diagram that should not drill
- Large composite architecture that should drill
- Edit of an existing diagram
- Explicit LR and explicit TB requests

For each prompt, capture native `--prompt` output and external-assistant `--mermaid`
output. Record the model and prompt/rules version used.

Measure four categories:

#### Structural

- Node and edge counts
- Subgraph count and membership coverage
- Maximum in/out degree and total connection count
- Cylinder and rhombus presence where semantically expected
- Drill count, drill depth, and seeded-child node count

#### Render health

- Mermaid parse and conversion success
- Node overlap and label clipping
- Edge crossings where measurable
- Canvas occupied area and extreme aspect ratios
- Elements falling outside their intended subgraph container

#### Semantic coverage

- Required concepts from the prompt represented in the graph
- Domain-appropriate labels
- Correct composite-versus-leaf treatment
- Preservation of existing nodes during edits

#### Visual quality

- Render screenshots for both paths at a fixed viewport and theme
- Use a small human or model-graded rubric for readability, hierarchy, grouping, and
  apparent completeness

Structural checks alone cannot prove visual parity. A graph may contain the correct number
of subgraphs and shapes while still having poor layout or missing the user's intent.

### Phase 1 — Complete `SKILL.md` prompt parity (implemented)

PR #18 added the seven previously missing or weak rules and rewrote the shape/color
introduction to state:

- Shared server normalization provides a limited safety net.
- V2 rendering supplies the final visual style for both paths.
- The assistant controls the graph structure that makes that styling effective.
- Subgraph membership matters more than explicit fill directives under V2.

Fallback `style` examples are retained only for older/non-V2 compatibility and are labeled
accordingly.

Run the Phase 0 evaluation before and after this change. Do not assign a numerical impact
estimate until the results support one.

### Phase 2 — Expand the authoritative local format contract (implemented)

`vaxis diagrams format --json` remains an offline CLI response and now exposes a
versioned Mermaid authoring contract.

The contract includes machine-readable fields for:

- Rules schema/version
- Richness rules
- Domain vocabulary rules
- Shape-selection contract and storage keywords
- Subgraph and topology guidance
- Direction rules
- Drill selection and seeded-child substance
- Preservation rules

The versioned JSON artifact is embedded by the CLI, and tests validate its version and
required skill content to reduce independent prose drift.

### Phase 3 — Add only proven deterministic server improvements

Use Phase 0 results to decide which remaining gaps can be fixed safely without an LLM.

#### Direction — implemented

Direct-Mermaid requests now accept optional context:

```json
{
  "mermaid": "...",
  "direction_context": {
    "policy": "preserve|auto",
    "explicit": "LR|TB",
    "is_fresh_generation": true,
    "viewport": { "width": 1440, "height": 900 }
  }
}
```

The default preserves existing behavior. Server auto-direction is an opt-in safety net,
not a silent rewrite. The CLI exposes matching flags and omits `direction_context`
entirely when none are supplied, preserving the legacy request body.

#### Thin seeded drills — implemented as measurement and warning

The CLI measures and warns before sending a non-empty seed below the three-node substance
floor. It does not silently filter content because a concise child may be legitimate, and
bare markers intentionally create empty children. Any future enforcement must:

- Never drop bare markers.
- Apply the floor only to non-empty seeded Mermaid.
- Prefer warning metadata over silent deletion.
- Add regression tests for concise valid children.

### Phase 4 — Eliminate cross-repository rule drift

The authoritative contract is now exported by `vaxis` from
`packages/scene-serializer/src/diagramAuthoringRules.ts` and served through the
authenticated `GET /api/diagrams/rules` endpoint. The CLI keeps an embedded, versioned
offline contract for `diagrams format --json` and compares it with the server through
`vaxis diagrams rules-check --json`.

`rules-check` returns status `0` for a compatible contract, `1` for operational errors,
and `2` for successfully fetched but incompatible contracts. The remaining Phase 4 task
is to run this comparison in a configured cross-repository CI/release environment; unit
tests already cover the high-value schema, storage-keyword, and seeded-drill comparisons.

### Phase 5 — Turn the evaluation into a regression suite (partially implemented)

- Deterministic structural and render-health checks now run in the repositories' CI tests.
- Run model comparisons periodically or before prompt/model upgrades.
- Pin model versions when reproducibility matters and record them with results.
- Store representative screenshot pairs and review substantial visual changes.
- Track native versus external-assistant scores over time instead of relying on anecdotal
  comparisons.

## Acceptance criteria

Item 7 is complete when:

1. `SKILL.md` accurately describes the shared server and V2 rendering behavior.
2. The assistant rules cover richness, domain language, grouping, topology, direction,
   shapes, drills, and preservation.
3. `diagrams format --json` exposes a versioned machine-readable authoring contract.
4. Direct Mermaid does not silently apply context-dependent direction changes without the
   required context or an explicit opt-in.
5. Bare drill markers remain supported.
6. A fixed evaluation set compares both paths across structural, render, semantic, and
   visual criteria.
7. The revised external-assistant path shows a measured improvement over its baseline and
   no regression in parse/render reliability.
8. Rule drift between `vaxis` and `vaxis-cli` is detected automatically.

“Parity” should not require byte-identical Mermaid or identical screenshots. It means the
two paths meet the same quality thresholds for semantic completeness, readable hierarchy,
render reliability, and visual organization.

---

## Recommended sequence

1. Build the Phase 0 baseline and record current scores.
2. Implement the Phase 1 `SKILL.md` corrections and re-run the baseline.
3. Expand and version the local `format --json` contract.
4. Implement only deterministic server changes supported by measured failures.
5. Add the cross-repo drift mechanism.
6. Promote stable evaluation checks into CI.

This sequence makes each claimed improvement measurable and prevents server changes from
being added for problems already solved by better graph authoring.
